# Kempower replay: protocol

Written on 2026-09-25, before any recorded program has run on Kempower input and before the
code that runs the replay exists. It is registered by the commit that adds it, together with
[programs.json](programs.json) and the inventory code that checks it, which runs no program.
It is not edited after that commit; changes are appended under Deviations.

## Question

RQ4b asks how transformation scripts generated by language models compare with
metadata-driven transformations in correctness and in robustness to configuration changes and
new vendors. The September runs ([findings.md](../findings.md)) measured generated programs on
MX Electrix and ProCem, two vendors the contract describes. Kempower is the first vendor that
none of the programs, prompts, examples or contract sentences was written for. This replay
runs the same programs on it, with no new model call, and asks where their output departs
from the engine's: in what the contract never described, or in what it did.

## Why this is a fair unseen test

- The programs were generated on 2026-09-15 and 2026-09-17. Kempower data was landed on
  2026-09-22 and its rulebook written on 2026-09-23. No program could have seen it.
- The programs are replayed, not generated again. No model is called, so no information about
  Kempower reaches any model, and the result does not depend on what a provider serves today.
- The oracle is the engine the recorded results used. On 2026-09-25 the current engine
  (`5a25726`) reproduced all 14 frozen MX Electrix and ProCem cases exactly, rows and
  statistics, so on every input behind the September scores it is the same oracle.
- Kempower is a wide source, like MX Electrix, and it has three constructs the contract does
  not describe. The comparison can therefore separate the contract's gaps from the models'
  own errors, which is what the reference interpreter (below) is for.

## What the contract covers for Kempower

Construct by construct, against the frozen contract (`CONTRACT.md`, SHA-256 `325cc47c89a5...`):

| Kempower rulebook | Contract | A program that follows the contract writes | The engine writes |
|---|---|---|---|
| `shape: wide`, five `columns`, `transform: none` | described (4.5, 5) | one row per non-null cell | the same |
| `device_id_template` without placeholders | described (4.2) | `kempower:public_passenger_dataset` | the same |
| `defaults.aggregation: average`, `defaults.interval_s: 10` | described (4.5, 2) | the same | the same |
| record rules `not_null` with `reject_row`; quantity rules `range` with `flag_suspect`; the `entity: measurement` value rule | described (3, 4.1, 4.6) | the same | the same |
| a column's own `aggregation: instantaneous` (`soc`, `tempC`) | not described: a wide column takes the default aggregation (4.5) | `average` on every state of charge and temperature row | `instantaneous` |
| `record.row_id_from: payload_position` | not described: the row id is the record's `row_id_field`, default `id` (4.4) | a null `source_row_id`, since the records have no `id` | the row's position in its landed part |
| `session` block | not described: the output has 16 fields and no session rows (2) | nothing | `session_id`, `ts_session_offset_s`, one `charging_session` row per session |
| no clock time | half described: a null timestamp gives a null `ts_utc` (4.3), but a record without the timestamp field is not mentioned | a null `ts_utc`, or a crash | a null `ts_utc` |

The identity hash (6) is built from `source_vendor, device_id, ts_utc, quantity, phase,
variant, harmonic_order, aggregation, source_row_id`. With one device, no clock time and no row
id, a program that follows the contract gives every reading of a quantity the same identity.

## Programs and arms

| Arm | Programs | Role |
|---|---|---|
| Primary | the interpreter programs of kimi-k3 and codestral-2508, 10 each | the test the plan named |
| Secondary | the interpreter programs of phi4-14b, 10 | reported, not headlined |
| Floor | the 30 snapshot programs | their configuration is another vendor's, written in; they show what per-vendor generated code gives a new vendor |
| Control | the reference interpreter | the contract's ceiling: what any program that follows the contract exactly would write |

Each sample is replayed as its final attempt, the program after repair, which is how the
September results describe a sample on the other vendor and on drift. 24 of the 60 final
programs are repairs. phi4-14b's programs come from its corrected run (`results/phi4-14b`), not
the superseded first one.

In interpreter mode a program receives the Kempower rulebook as the harness builds it for any
vendor, with the unchanged `rulebook_from_bundle`: the source schema keys in `SOURCE_KEYS` and
the list of field names (so the `session` block is not shown), the mapping, the validation
rules and `measurement_id_from`. Snapshot programs receive the records only.

## Inputs

Three cases of the `test` split, written to `kempower_replay/cases/`:

- **golden_edge**: the six synthetic records of the golden contract, landed as one Parquet
  payload in partition `export=0f1e2d3c/part=00000-c000` and read back through the reader. They
  hold two readings at one session offset, a missing temperature, a state of charge above 100,
  a negative voltage and a record without a session. The engine writes 24 rows (2 suspect),
  rejects 1 record, skips 1 null cell and writes 2 sessions.
- **real_part_start**: the first 200 records of part `00000-c000`, in payload order.
- **real_part_spread**: 400 records of part `00049-c000`, the middle of the 99 landed parts, at
  positions floor(i × 736,669 / 400) for i from 0 to 399.

Records reach a program exactly as the engine receives them from the reader, including the
reader's `_payload_position` stamp, because the harness gives a program precisely what the
engine receives. `device_factors` is empty. If a selected record holds a value that JSON cannot
carry exactly (NaN or infinity), the builder stops, and the case is recorded as a deviation
rather than altered.

The engine's output for each case comes from the harness's unchanged oracle, `run_engine`,
which runs the engine on the same rulebook the programs receive, without the `session` block.
The session block changes no scored field, and the builder checks this: for every case, the
engine run on the full rulebook must give the same rows on every scored field and the same
statistics. The session rows reported under measure F come from that full run.

## Measures

Execution is the September harness unchanged: the same static check, the same interpreter
flags and stripped environment, 60 seconds per input, one run per program per input.

The primary outcome is, for each primary model, the contract-exact count (measure B) and the
classification of the other programs, with the strict count against the engine (measure A)
beside it.

- **A. Against the engine**, with the unchanged scorer (`codegen/compare.py`): runs, pass,
  pass with timestamps as instants, statistics exact, identity hash and row F1, as README.md
  defines them. A pass needs all three inputs.
- **B. Against the contract**: the same scorer with the reference interpreter's output as the
  oracle. A program is *contract-exact* when it passes, its statistics equal the reference's
  and every identity hash equals the reference's, on all three inputs.
- **C. Where the departures sit**: rows compared as multisets after projecting them onto fewer
  fields, with the same numeric tolerance. Every level also requires statistics equal to the
  engine's. Level 1 is every contract field (measure A's pass). Level 2 leaves out
  `measurement_id` and `source_row_id`, setting the row id aside. Level 3 also leaves out
  `aggregation`, setting per-column aggregation aside. A program's level is the highest it
  reaches on all three inputs.
- **D. Identity**: distinct `measurement_id` values per input, against the number of rows.
- **E. Beyond the contract** (exploratory, no prediction): programs that agree with the engine
  where the contract's reading does not, for example a column's own aggregation or a non-null
  row id.
- **F. Sessions**: structural. The contract's output has no session fields and no session rows,
  and the scorer never scores session fields (`oracle.RUNTIME_FIELDS`). Every program's session
  coverage is zero by construction. The engine's session rows, from its run on the full
  rulebook, are reported for scale, and the zero is not counted as a model failure.

## Predictions

Written before any program ran on Kempower, and reported whether or not they hold. P4 rests on
the published September results, not on reading any program for this test.

- **P1.** No program, and not the reference, passes against the engine on any Kempower input
  (measure A). The contract gives no way to write the engine's row id or a column's own
  aggregation.
- **P2.** The reference runs on all three inputs and departs from the engine in exactly three
  fields: `source_row_id` (null on every row), `aggregation` (`average` on every state of
  charge and temperature row, 9 of the 24 rows of golden_edge) and therefore `measurement_id`.
  Every other field and all seven statistics equal the engine's. So the reference reaches level
  3 and not level 2.
- **P3.** Identity collapses. The reference writes one `measurement_id` per quantity present,
  at most 5 per input, where the engine writes one per row (24 on golden_edge). The canonical
  table merges on `measurement_id`, so a load that followed the contract would keep 5 Kempower
  rows, however many it read.
- **P4.** Against the contract (measure B): at least 7 of kimi-k3's 10 interpreters are
  contract-exact, 2 to 5 of codestral-2508's, and at most 1 of phi4-14b's. For both large
  models, programs shown MX Electrix, the wide shape Kempower shares, do at least as well as
  those shown ProCem. The reasons: most of kimi-k3's September failures on the other vendor
  came from one reading of `phase_map`, and Kempower has no generated rules; most of
  codestral-2508's came from programs that handle only the shape they were shown.
- **P5.** No snapshot program writes a row equal to a row of the reference's output.

## Classifying failures

The rule of findings.md applies unchanged, with two additions fixed here, before any failure
is seen:

1. **The point of comparison.** Criterion 3 (with the point set aside, the output equals the
   oracle's) is checked against the reference's output, not the engine's, because the engine
   implements constructs the contract does not describe.
2. **A new class: outside the contract.** A departure from the engine in a field the contract
   does not govern for this source (`source_row_id`, `measurement_id`, the aggregation of state
   of charge and temperature, and any session field) is attributed to the contract, never to
   the model. A program whose only departures are of this class, or permitted readings, is
   *correct on everything the contract describes*.

Points where the contract is silent or admits two readings, declared now as the only scope for
permitted readings:

- (a) Section 4.3 says a null timestamp gives a null `ts_utc`; it does not say what a record
  without the timestamp field gives. Every Kempower record lacks one.
- (b) Section 1 names JSON and delimited-text sources; Kempower is a Parquet export, whose
  values arrive typed, as JSON's do.
- (c) The contract does not say whether a rulebook key it does not describe (`row_id_from`, a
  column's `aggregation`, `format.type: parquet`) is to be ignored, followed or refused.
- (d) Section 4.5 walks `mapping.columns` and then `mapping.generated`, and does not say that a
  wide rulebook may have no `generated` entry. Kempower's has none.

Anything else is a defect: a wrong value, a missing or extra row, a crash on something the
contract makes explicit (a missing `id` field gives a null row id, Section 4.4; `meter_field`
applies only when declared, Sections 4.2 and 4.4), a refused import or a timeout. Examining a
sample stops at its first clear defect. The report gives the strict count, the contract-exact
count and the count correct on everything the contract describes, side by side. The strict
score is never adjusted.

## Validation before the replay

The replay does not start until every gate holds, and each outcome is recorded in the results:

- **G1.** `python harness.py selfcheck` passes, unchanged.
- **G2.** The engine at the frozen commit reproduces the 14 September cases exactly.
- **G3.** `python harness.py inventory` passes: every program matches programs.json and a
  cached reply.
- **G4. Positive control.** The reference interpreter with the three Kempower constructs added
  (a column's own aggregation; the row id taken from `_payload_position` when `row_id_from` is
  `payload_position`) passes against the engine on all three inputs, statistics and identity
  hashes included. This shows that a pass is reachable on these cases, so a zero is not the
  harness's.
- **G5. Negative control.** G4's program with the voltage range rule ignored fails golden_edge,
  and the scorer names quality as the difference.
- **G6.** Nothing frozen has moved: `git diff 5a25726 -- src` in `secha-transform` and
  `git diff 9170d3e -- canonical vendors/kempower targets tests/fixtures/kempower` in
  `secha-metadata` are empty, and the provenance shows neither working tree dirty.
- **G7.** No model call. The replay never constructs a model client, and a test runs it with
  network access refused.

The replay code (the case builder, the `replay` command, the projection scorer and the two
controls) is written and unit-tested on synthetic inputs, and committed before the replay. Its
commit is recorded in the results. It may not change anything this protocol fixes. The
controls are harness code and are never scored as subjects.

## Procedure

1. Register this protocol, programs.json and the inventory code by committing them.
2. Write and test the replay code; commit it.
3. Build the three cases into `kempower_replay/cases/`, recording the input digests and the
   engine's output in its manifest.
4. Run the gates G1 to G7.
5. Run the replay once: every program in programs.json and the reference, on every input.
6. Classify failures under the rule above, and write the results into findings.md as a new
   section that links this protocol.

The replay runs once. A second run is allowed only for a fault in the harness (a gate found
failing after the run started, or the sandbox failing to start a program), and is recorded as
a deviation with both runs kept.

## Data governance

- No model is called, and nothing leaves this machine.
- Kempower records are partner-confidential. The real ones stay in `kempower_replay/cases/` and
  `kempower_replay/results/`, both gitignored, and are used only inside the local sandbox.
- Committed files carry counts, digests and field names only, never a measured value from a
  real record.

## What the result can and cannot show

- It measures whether frozen generated programs transfer to a source shape none of them saw,
  and it separates the contract's gaps from the models' own errors.
- It cannot show whether a model shown Kempower would write a correct program. That needs new
  generations and is outside this test.
- The comparison is asymmetric on purpose. The engine was extended for Kempower with five
  generic capabilities (+243 lines of code, no vendor logic; onboarding diary, Step 4); the
  programs were frozen. A frozen program against a framework that absorbs a new shape through
  generic code and configuration is the comparison RQ4b asks for. The engine's cost comes from
  the diary; this replay measures nothing new on the engine.
- The numbers are small: 10 programs per model and mode, three inputs.
- We wrote the contract, the reference interpreter and the Kempower rulebook. The reference
  matched the engine on all 14 September cases; on Kempower it is predicted to differ (P2), and
  that difference is part of the result.
- The author read programs during the September classification. P4 rests on those published
  results.
